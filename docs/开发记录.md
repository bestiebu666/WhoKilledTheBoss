# 办公室八卦 Demo · 第一幕

Godot 4.7.2 工程。**第一幕 = 设计部灰盒 + 点击探索 + 判断题**。  
世界变色是第二、三幕的事，这个工程里没有。

**现在从「进入页」开场，不再一打开就直接进地图：**

```
标题页 ──「开始游戏」──→ 选幕页 ──点「第一幕」──→ 办公室地图（main.tscn）
	 └──「前情提要」──→ 前情提要 + 引导剧情（逐段点开）──→ 选幕页
```

第二幕、第三幕是**锁住的**（灰底灰字，点了只给一句提示，不会进游戏）。  
想开哪一幕就改 `data/frontend.json` 里那一项的 `locked` 和 `scene`。

**视角是「悬浮记录仪」**：相机吊在 **3.0 米**高、跟着你走，俯视看整间 ——  
主角是一件「神器」，本来就该高高在上，不是 NPC 的同事。按住鼠标左键拖动看四周，点地面就走过去。  
**主角完全不做建模**：玩家节点只有一个胶囊碰撞体，没有任何可见网格，低头也看不到自己。

**房间 16×12 米、层高 4.5 米，四面满高墙 + 一整块天花板 + 地板。**  
视角可以抬头（`pitch` 上限 +22°），抬头看到的是天花板和一盏吊灯 ——  
不是天空、也不是建模边界。天花板被单独放在一个光照层上，所以吊灯不会把它烤成一块白斑。

## 操作

| 动作           | 做什么                        |
| ------------ | -------------------------- |
| **按住鼠标左键拖动** | 环顾四周（左右转 + 往下可看脚下、往上可看天花板） |
| **点地面**      | 走过去                        |
| **点物件 / 点人** | 走到跟前 → 弹信息卡 / 出题           |

## 收到别人做好（或 AI 生成）的模型，怎么接进去

交付过来的 glb 往往**尺寸、朝向、原点、面数、贴图都不符合游戏要求**（尤其 Tripo 之类的  
AI 生成模型：十多万面、2048 贴图、原点在奇怪的地方）。`tools/` 里有三个无头 Blender 工具，  
按顺序跑：

```bash
# 1) 先看一眼：节点、面数、贴图、包围盒、原点对不对
python tools/glb_info.py "D:/桌面/办公桌.glb"

# 2) 不确定长什么样/朝向哪边，出一组四视图（正/侧/顶/斜）
"D:/blender/blender.exe" --background --python tools/model_probe.py -- \
	"D:/桌面/办公桌.glb" "./docs/probe"

# 3) 归一化：等比缩放到指定宽度 → 原点移到底面中心 → 只留 Base Color、贴图降到 1024
#    → 对象名改成模型名 → 导出
#    （最后一个参数是减面上限，**传 0 = 不减面**。作者要求保留原始精度，默认就传 0。）
"D:/blender/blender.exe" --background --python tools/model_fit.py -- \
	"D:/桌面/办公桌.glb" "./assets/models/SM_F_DeskBench.glb" \
	"SM_F_DeskBench" 3.86 0 1024
```

`model_fit.py` 还会打印**高度剖面 / 深度剖面** —— 用来确认「桌面在哪、椅子在哪一侧」：  
桌面高度定缩放比例，深度剖面能看出模型朝哪边。这个项目的做法是**照桌面高度定尺寸**  
（桌面 = 0.6 米，和原来灰盒桌子一样高），这样家具和 1.04 米高的 chibi NPC 比例才对得上。

### 一次交来一堆？用批量版 `model_prep.py`

`model_fit.py` 一次只吃一个文件，而且每次都从「宽度」缩。收到一整批资产（比如  
2026-10-05 前后那两批，一共 13 件）时改用 **`tools/model_prep.py`** —— 它吃一份清单 JSON，一件一件跑：

```bash
"D:/blender/blender.exe" --background --python tools/model_prep.py -- tools/model_prep_list.json
```

清单长这样（`tools/model_prep_list.json` 就是实际在用的那份）：

```json
{ "src": ".../沙发.glb", "name": "SM_F_Sofa",
  "fit": "width",        // height / width / depth / max —— 按哪个轴等比缩放
  "target": 3.90,        // 该轴的目标米数（等比，绝不拉伸）
  "stretch": [1.0, 1.0, 0.55],  // 单轴拉伸（只乘某几个轴），默认 [1,1,1]
  "tex": 2048,           // 贴图最长边上限（0 = 保持原分辨率）
  "tint": "#F2836B",     // 换色：按亮度重映射（不写 = 不动）
  "yaw": 180,            // 绕竖轴预转多少度（把模型的正面转到 -Z）
  "decimate": "none",    // none（默认，不砍面）/ planar（只合并共面三角形）/ collapse
  "tris": 0,             // 只在 decimate=collapse 时当上限用
  "weld": true,          // 焊掉重复顶点（零视觉损失），默认开
  "probe": true }
```

**`stretch` 是「只改一个维度」时的唯一正确做法**（旧名 `squash` 仍兼容 ＝ `stretch` 只给一个数）：

```jsonc
"stretch": 0.55                        // 只乘高（Blender Z）—— 地毯压薄
"stretch": { "axis": "x", "k": 1.173 } // 只乘某一个轴
"stretch": [1.1729, 1.0, 1.32]         // [X, Y, Z] 各乘各的 —— 门的「先拉高 80 再拉宽 80」
```

⛔ **别用 `fit` / `target` 去改单个维度** —— 那是**等比**缩放，改一个轴会把另外两个一起带走。  
磨砂门要「拉高 80 厘米」，如果把 `target` 从 2.5 直接改成 3.3，宽度会跟着涨到 6.11 米，  
一扇门就变成一个 6 米宽的洞。轴的含义：**Blender X = Godot 宽 x，Y = 深 z，Z = 高 y**。

比 `model_fit.py` 多出来的几件事，都是这批资产逼出来的：

- **按轴缩放**：沙发要按宽度（3.90 米）缩、服装展架要按高度（1.95 米）缩，不能一律按宽度。
- **`yaw` 预转**：AI 生成器给的模型**正面几乎都朝 `+Z`**，和这个工程约定的 `-Z` 正好相反。  
  在清单里写 `"yaw": 180` 就把它转正 —— 导出的 `.glb` 朝向就是对的，`room.json` 里照常写 `rot`。  
  （2026-10-05 第二批的 5 件全是这样。）
- **四视图自检**：正 / 背 / 俯 / 斜 拍一张拼图到 `docs/probe_prep/`。  
  **判朝向要看第 1 格**（规格说明见下面「血泪教训 三」）。
- **焊重复顶点**：AI 生成的模型经常是「每个三角形各自三个顶点」的散装网格，合掉它们是零视觉损失的清理。  
  ⚠ **拓扑良好的封闭网格别开** —— 那会把 UV 缝上的重合顶点也焊掉，贴图接缝错位。  
  判断方法：看顶点数 ≈ 面数 × 0.5~0.6（正常）还是 ≈ 面数 × 3（散装）。
- **`probe_only`**：只出图不导出，用来单纯确认朝向。

### ⚠️ 三条血泪教训（2026-10-05 补）

**一、四视图必须在「材质瘦身 + 减面」之后渲染。**

最初的版本把 `render_sheet()` 写在了减面**之前**，于是自检图里看到的一直是**还没被动过的**  
原始模型 —— 减面把网格撕成什么样，四视图永远验不出来。作者点进游戏才发现「好多表面碎掉了」。  
现在 `model_prep.py` 里四视图是**最后一步**（导出前）。改脚本时千万别把这个顺序调回去。

**二、默认不砍面。塌缩减面在低于 20% 时是毁灭性的。**

作者原话：**「你不要砍我的建模面数，点进游戏里发现建模都崩了，好多表面碎掉了」**。  
当时干的蠢事：

| 资产      | 原始面数      | 砍成     | 剩     | 后果       |
| ------- | --------- | ------ | ----- | -------- |
| 发财树 1   | 1,499,754 | 2,500  | 0.17% | 树冠碎成渣    |
| 实习生 1 号 | 947,125   | 3,999  | 0.42% | 脸和衣服破裂   |
| 沙发      | 1,500,000 | 23,999 | 1.6%  | 坐垫上一片片破洞 |
| 饮水机     | 50,000    | 1,500  | 3%    | 外壳破面     |

**COLLAPSE 减面是合并边来省面的**，比例一低就会把不相干的顶点焊到一起，  
模型表面上就出现一片片「被撕开的」三角破洞（尤其 AI 模型本来就有很多断开的小壳）。  
所以：

- 默认 `decimate: "none"`，原样交付。1.5M 面的沙发就是 1.5M 面，48 MB 就 48 MB。
- 真要减，只能用 `"decimate": "planar"` —— 它只合并夹角极小的**共面**三角形，  
  外形不变、UV 靠 `delimit={"UV"}` 保住。但它对曲面（圆润的坐垫、树叶）几乎无效。
- 面数预算的语义跟着改了：**「已交付」的槽位 `tri` 直接写实测面数**，  
  看到 `1497046` 不要以为写错了。

**三、四视图哪一格是「正面」？第 2 格。而且 `yaw` 会被静默吃掉。**

2026-10-05 第二批（4 件服装展架 + 1 座雕塑）踩的坑，两条都极难自查：

**(a) 四视图格序**。glTF 导入 Blender 的映射是 `(x, y, z)_gltf → (x, -z, y)_blender`，  
所以 **glTF 的 `-Z`（约定正面）在 Blender 里是 `+Y`**，而拼图的

| 格         | 相机               | 看到的是                                  |
| --------- | ---------------- | ------------------------------------- |
| **第 1 格** | 站在 `-Y` 往 `+Y` 看 | glTF **`+Z`** 侧 —— 模型若守约定，这一格是它的**背** |
| **第 2 格** | 站在 `+Y` 往 `-Y` 看 | glTF **`-Z`** 侧 = **约定正面**            |

判「要不要转 180°」就看**第 1 格**：第 1 格是正脸 → 它朝 `+Z` → 要转。  
（原来脚本里那句注释写反了，2026-10-05 用 `SM_F_DeskBench` 实测订正 —— 它的椅子在 `-Z` 侧，  
而**第 2 格**才看得见椅子。）

**(b) `yaw` 静默失效**。Blender 的 glTF 导入器把物体的 `rotation_mode` 设成了 `QUATERNION`，  
这时赋 `rotation_euler` **不报错、不警告、尺寸也不变** —— 看起来就像「转过了」。  
第二批 5 件全部转了 180° 却一个都没转，还差点以为是模型本身左右对称。  
**必须先 `obj.rotation_mode = "XYZ"` 再赋值。**

怎么发现的：把「源模型四视图」和「导出后四视图」做**像素级比对** ——  
同格平均差只有 `0.0001`（等于没动），但**交叉比对**（源的第 1 格 vs 成品的第 2 格）却是 `0.016`。  
修好后同格差升到 `0.015`、交叉差降到 `0.003`（两格互换了）。**别靠肉眼，眼看不出来。**

> **贴图同理，别压太狠**：`img.scale(512)` 对**烘焙图集**（岛与岛之间填深色缝的那种）  
> 下手太狠 —— 缝会比面还宽，模型上看着像裂了。现在统一上限 2048（源图 4096 → 2048）。

### NPC 的待机动作与互动（2026-10-05 加）

四个角色交来时都是**单张静态网格 —— 一个节点、一个 mesh、没有骨骼也没有蒙皮**  
（`glb_info.py` 里就是「节点 1 / 网格 1」）。所以**播不了骨骼动画**，改用  
「骨架之外的程序化表演」：全部在 `scripts/main.gd` 里算，不依赖任何美术资产。

- **呼吸** —— 只走枢轴的 **scale**（枢轴在鞋底，所以是「从脚往上涨」），  
  同时极轻微地压扁/拉长（squash & stretch）。两者反相：涨上去就瘦、沉下来就胖。  
  **脚底一点不动。**
- **站姿** —— 绕脚底前后左右各晃 1° 上下，两条不同频率的正弦叠加，不像机器在摆。
- **偶尔动一下** —— 一条很慢的波取 14 次幂，绝大部分时间 ≈ 0，峰值附近才突起一个  
  「换重心 / 抬头」。约 20 秒一次。
- **看你** —— 走进 2.4 米以内才慢慢转头，而且是**渐入**的（0.9 米内才转满）；走开再转回去。
- **被点** —— 点它会「一顿」（点头 + 往下坐 + 轻微压扁），然后自己回到待机。

三个实现上的关键点，改动时别弄丢：

1. **动作只作用在「脚底枢轴」上。** `_npc_make_pivot()` 在 NPC 的宿主 `StaticBody3D`  
   下面插一个 `Node3D`（名字叫 `Anim`，位置在鞋底），再把**灰盒和真模型一起 reparent 进去**。  
   转它 = 整个人绕脚底晃；缩它 = 从脚往上涨。**碰撞体一点不动** —— 那是 `StaticBody3D`  
   的固有形状，动画只碰视觉，不然走路会被一个会呼吸的碰撞体顶来顶去。  
   ⚠ 副作用：`body.get_node("Greybox")` 找不到灰盒了，得用 `find_child(...)` 递归找。  
   自检里的 `_grey()` 就是这么崩过一次的。
2. **走 `_process` 而不是 `_physics_process`。** 物理帧 60Hz 和显示刷新率对不上，呼吸会抖。
3. **每个人按 `id` 派生相位/频率/幅度**，同一个人每次进游戏表现一致，不同的人互不相同 ——  
   不然四个人像三胞胎同步做操。

想调某个人「活分」到什么程度，在 `data/objects.json` 里给他加一项（不写就是 `{1, 1}`）：

```json
"idle": { "speed": 0.5, "amount": 0.4 }
```

`speed` = 整体快慢（频率），`amount` = 整体幅度。写 0 就是完全定住。  
老板用的就是 `{0.5, 0.4}` —— 他陷在沙发里休息，用轻快节奏会显得很出戏。

> #### ⛔ 硬规矩：枢轴的 `position.y` **只许往下沉，不许往上抬**
>
> 作者原话：**「一靠近像气球一样飘起来了」**。原因就是第一版把呼吸做成了  
> `pivot.position.y = base_y + 0.020 * sin(...)` —— 枢轴在鞋底，`position.y` 一加减，  
> **整只脚就跟着离地 2 厘米**；「被点弹一下」那 4.5 厘米更离谱。  
> 现在：呼吸全部交给 `scale`（脚是缩放原点，永远贴着地），  
> `position.y` 只用来做**下沉**的体重感（`base_y - sink * ...`，`sink` 现在 5 毫米）。
>
> 实测（`res://scenes/npcdiag.tscn`，站在身边 150 帧取样）：
>
> | 距离    | 脚底起伏   | 转头                            |
> | ----- | ------ | ----------------------------- |
> | 5.0 m | 3.2 mm | +5.6°                         |
> | 3.6 m | 1.8 mm | **+1.3°**（上一版在这个距离已经猛拧到 116°） |
> | 2.6 m | 1.3 mm | +0.3°                         |
> | 1.6 m | 2.7 mm | −63.5°                        |
> | 0.8 m | 3.7 mm | −130.2°                       |
>
> 上一版脚底起伏是 **19~25 毫米**。自检用 `_vis_bounds()` 把这条钉死了。  
> ⚠ 量的时候取**局部包围盒的底面中心**，别取 8 个角 —— 身体一倾斜，  
> 那些角会甩出十几毫米的假位移（AABB 是个松垮的盒子），第一版就是这么误判成 FAIL 的。

### 头顶的二次元思考框（2026-10-05 加）

走近 NPC（2.6 米以内）头顶会自动「啵」地弹出一个漫画式的思考框，走开收回去。

**它是程序画出来的，仓库里没有任何 png。** `scripts/thought_bubble.gd` 按  
`data/objects.json` 的 `_bubble` 参数在运行时把贴图渲染出来，参数一样的人共用一张（缓存住）。  
好处是形状完全可调 —— 改个数字重开就换样子，不用重新导图。

**四个人的形状各不一样**（作者从一张漫画对话框参考图上点了左边那一列，从上到下对应过来）：

| 谁      | 形状           | 是什么             | 关键参数                                   |
| ------ | ------------ | --------------- | -------------------------------------- |
| 凤凰男    | `spike`      | 锐利星芒（震惊 / 炸毛）   | `bumps` 11 根刺、`spike_sharp` 1.45 让边往内凹 |
| 实习 1 号 | `box_tail`   | 圆角方框 + 左下角一条尾巴  | `bw/bh/bcorner`、`tail_*`               |
| 老板     | `cloud`      | 扇贝边云朵 + 底下一圈放射线 | `bumps` 10、`rays` 9                    |
| 总监     | `panel_tail` | 斜格面板 + 尾巴 + 网点  | `tilt` / `skew` / `halftone_*`         |

另外还留着没删的：`burst` 爆炸锯齿 / `round` 素圆 / `square` 骨架圆盘密排出的方框。

```json
"feng": { "bubble": {
  "style": "spike", "range": 2.6, "h": 0.86, "lift": 0.05,
  "bumps": 11, "jitter": 0.34, "spike_amp": 0.46, "spike_sharp": 1.45,
  "outline": 11, "sx": 1.06, "sy": 1.0, "double_line": 1,
  "dots": 0,            // 底下那三个递减小圆。四个形状自带尾巴/射线，所以都关了
  "text": ""            // 内容。现在空着 —— 填这儿就行，不用重画贴图
}}
```

`data/objects.json` 的 `_bubble_note` 里有逐项说明（每个形状专属的参数也列在那儿）。

**四条实现上的关键点：**

1. **轮廓一律存成一张 `R(θ)` 表**（从形状中心朝 θ 射一条线，交在多远），  
   判断内外退化成一句「距离 < R(θ)」。前提是形状**相对中心是星形的**：
   - 云朵 / 素圆 / 方框：**一堆圆盘的并集**（`_table_disks`），边界天然扇贝形。
   - 星芒：三角波给半径，`pow(tri, spike_sharp)` 指数 > 1 就把边往里压成细长的尖刺。
   - 方框+尾巴 / 斜格面板：**多边形**，`_poly_table` 对每条边做射线求交、  
	 取**最远**的那个交点当外轮廓（尾巴直接长在底边上、中间没有缝，所以最远交点就是外轮廓）。
2. **形状空间里 `+y` 是朝下的**（朝着头顶 —— 底下那三个小圆就在正 y）。  
   所以 `_poly()` 是按「+y 朝上」的自然坐标系搭好、最后统一翻的，  
   写 `tail_tip_y = -1.62` 时脑子不用拧着，负数就是「往下伸」。  
   放射线的角度也按这个空间算：**90° = 朝下**。
3. **贴图里有没有那三个小圆，锚点不一样。** 带小圆时锚点是**贴图底边**（小圆要指着头顶）；  
   不带时锚点是**形状自己的下沿**（否则形状和头顶之间会空出一大块白）。  
   放射线长在轮廓外面、`R(θ)` 表量不到，得手工把它那截加进锚点，不然射线会戳进脑袋里。
4. **挂在宿主上，不是挂在枢轴上。** 挂在枢轴上会跟着呼吸/摇晃一起抖；  
   挂宿主上还有个好处：宿主绕 Y 转时框在转轴上，位置一点不动。  
   贴图走 `alpha_cut = DISCARD`（白色填充本来就不透明），不跟房间的发光 overlay 抢排序。  
   内容位 `Label3D` 必须 `no_depth_test = true`，否则换个相机方向就被白底盖住。

> **踩过的坑**：放射线**不能拿 `g` 去算覆盖度**。`g` 是「离轮廓的距离」，而射线整个位于  
> 轮廓**外面**，用 `g` 算出来最多 0.5（半透明）—— 表现是线画出来了但是**灰的，不是墨线**。  
> 现在射线单独带一个覆盖度出来。

### 沙发换色（多巴胺色系）

颜色**烘在贴图里**，改色靠 `tools/model_prep_list.json` 里沙发那条的 `tint`：

```json
{ "src": ".../沙发.glb", "name": "SM_F_Sofa", "fit": "width", "target": 3.9,
  "tex": 2048, "tint": "#F2836B" }
```

改色公式（`model_prep.py` 的 `recolour()`）是**按亮度重映射**，不是整体乘一个颜色：

```
参考亮度 ref = 全图亮度的 90 分位（≈ 那片浅色岛）
每个像素     out = 目标色 × (自身亮度 / ref)
```

因为交付来的贴图是**烘焙图集**（真正的表面是一片片浅色岛，岛与岛之间填深色缝）——  
整体乘色会把浅色一起压暗、整块发闷；填平均色又会把缝糊没、接缝全丢。  
按亮度重映射则：亮的地方正好落在目标色上，暗的地方（岛间的缝、烘焙的 AO）按比例压暗，  
**缝还在、明暗还在，但整块布变成了新颜色**。

> ⚠️ Blender 对 8bit 贴图的 `.pixels` 给的是**原始 sRGB 编码值，不是线性值**  
> （用已知灰阶实测确认过：写 0.5 进去读回来还是 0.5，不是 0.214）。  
> 所以目标色直接用 sRGB 分量，**千万别转线性** —— 一转整块布会亮一大截。

想换个颜色：把色号填进 `tint`、重跑 `model_prep.py`（只跑沙发约 40 秒）、再让 Godot 导入一次。  
想先看效果再决定，跑 `tools/sofa_palette.py` —— 它把同一块布料换成几组候选色拼成一张图  
（输出 `shots/沙发候选色.png`），**用的就是同一套公式**，所以图上相中哪组，填进去不会有偏差。

## 想调视角

`data/room.json` 的 `camera` 段，改完不用碰代码：

```json
{
  "eye_height": 3.0,
  "fov": 55,
  "yaw": -90,
  "pitch": -34,
  "mouse_sens": 0.13,
  "pitch_min": -80,
  "pitch_max": 22
}
```

| 值                         | 含义                                    |
| ------------------------- | ------------------------------------- |
| `eye_height`              | 相机离地高度。现在 3.0 米，远高于门（2.2）和 NPC        |
| `fov`                     | 视场角（垂直）。**和 `pitch_max` 绑死**，见下       |
| `yaw` / `pitch`           | 出生的朝向与俯仰（`yaw` -90 = 朝东；`pitch` 负数低头） |
| `mouse_sens`              | 拖动 1 像素转多少度                           |
| `pitch_min` / `pitch_max` | 俯仰上下限。**允许正数** —— 正数就是能抬头看天花板         |

**`eye_height` 决定「主角站在哪」**：1.68 是人眼高（会和 NPC 面对面，压迫感强），  
2.45 是比门略高，**3.0 是这版**（挂在天花板下方的记录仪，俯视全屋、俯视 NPC）。  
再往上要记得留出天花板的位置。出生点在同文件的 `spawn`。

**`pitch_max` 和 `fov` 是一对，必须一起改。** 规则只有一条：

```
pitch_max + fov / 2 < atan((墙高 − 相机高) / 到墙的最近距离)
```

左边是**画面最顶那条线的仰角**（不只是画面中心），右边是**打到墙顶需要的仰角**。  
现在 `22 + 27.5 = 49.5°`，而贴到墙边打中墙顶要 `atan((4.5−3.0)/0.36) ≈ 76°` ——  
49.5 < 76，所以抬到头看到的也只是墙和天花板，翻不到房间外面去。

⚠️ 别只调 `pitch_max` 忘了 `fov`：`pitch` 只决定画面**中心**的朝向，画面**顶部**还要再加半个视场角。  
（这个坑真踩过：只把 `pitch_max` 设成 `-4°` 就以为看不到上方了，结果 `-4 + 34 = +30°` 照样翘上去。）

**天花板为什么不吃吊灯的光**：相机只有 3 米高、离顶很近，灯的正下方必然过曝成一片惨白。  
所以天花板被放到**第 2 渲染层**，而每盏灯的 `light_cull_mask = 1`（只照第 1 层）——  
天花板只吃环境光，再补一点自发光（`emission 0.55`）当「地面反射回来的光」。  
改这段看 `main.gd` 的 `_build_shell()`。

### 画面滤镜 / 调色（多巴胺，2026-10-06 加）

作者原话：「模型到游戏里实况变得非常灰，要**高饱和、多巴胺、轻松活泼**；别改模型颜色，改整个环境色。」

做法：**一个模型的材质色、一个布景的 `color` 都没动** —— 全靠 `room.json` 的 `grade` 段  
（`main.gd` 的 `_build_environment()` 读）：① 环境光颜色 / 能量；② 全屏 `adjustment`（亮度 / 对比 / 饱和度）；  
③ 色调映射；④ 一点轻微泛光。

| 参数                                 | 现值                  | 作用                                                          |
| ---------------------------------- | ------------------- | ----------------------------------------------------------- |
| `tonemap`                          | `linear`            | ⛔ **别用 `aces`**：实测它会把高饱和色往白里压，再叠一点提亮就整体泛白，平均饱和度反而**低于不加滤镜** |
| `saturation`                       | `1.60`              | ★「多巴胺」主开关，灰感主要靠它救                                           |
| `contrast`                         | `1.20`              | 压掉灰蒙蒙的中间调                                                   |
| `brightness`                       | `1.02`              | 略提亮、显轻松。⚠ 提太多会泛白，反而降饱和                                      |
| `ambient_color` / `ambient_energy` | `#FFEDE2` / `0.55`  | 环境色给一点糖果暖调，米白的墙也蒙上一层薄薄暖粉                                    |
| `glow`                             | 开（`threshold 1.08`） | 只让窗 / 灯这些 HDR 超亮处晕开一点点，别的别动，否则全画面发糊                         |

想更浓 / 更稳：直接改 `grade` 里的数字（`saturation` `1.45` 更稳、`1.75` 更猛），**不用碰代码**。  
想全部关掉：`brightness`/`contrast`/`saturation` 都写 `1.0`、`glow.enable` 写 `false`。

⚠ 三个坑：

- `adjustment` / `glow` **只在 Forward+ 生效**（本项目就是，见 `project.godot`）。
- `_tonemap_of()` 里常量名拼错（是 `TONE_MAPPER_REINHARDT`，不是 `REINHARD`）会**直接 Parse Error、整个脚本挂**。
- 它只作用于 **3D 画面**；2D 的纸卡 / 文字 / 标题页**不受影响**（已核对 `00a_进入页_标题`）。

### 背景音乐（2026-10-06 加）

作者给了一条原始 WAV（`背景音乐.wav`，209.8 秒 / 44.1kHz 立体声），接进游戏做**全程循环**的 BGM。

**先说结论：WAV 不能直接丢进 Godot。** 三个理由：

1. **体积** —— 未压缩 35.3 MB；转 Ogg 后 **4.05 MB**（11%）。
2. **首尾安静段** —— 实测这条素材：**0.00~0.14s 是近乎无声的引子**（音乐 0.15s 才真正起）、  
   **尾部从 ~207s 开始收尾淡出、208.6s 后彻底静音**。原样循环 = 每轮回到开头先静一下、  
   到结尾又淡没 —— 音乐是「断」的。
3. **采样级接缝** —— 就算裁到「音乐还在响」的位置，直接首尾相接也会有跳变（「咔」）。

裁点是用 0.05 / 0.1s 窗 RMS **量出来**的，不是拍脑袋：

| 项      | 值              | 为什么                                                                                      |
| ------ | -------------- | ---------------------------------------------------------------------------------------- |
| 起点 `A` | **0.15 s**     | 音乐真正的 onset（前面那 0.15s 静音不要）                                                              |
| 终点 `B` | **206.00 s**   | 此处电平 **−21.9 dB**，与起点处的 **−23.2 dB** 只差 **1.3 dB** —— **接缝两边响度天然对齐**；再往后（207s+）就是编曲的收尾淡出 |
| 接缝     | **40 ms 交叉淡化** | `blend[s] = R[M-X+s]·(1−s/X) + R[s]·(s/X)`，`O = R[X:M−X] ++ blend`                       |

⚠ `blend` 必须接在**末尾**。若放到开头（`O = blend ++ R[X:M]`），循环点会变成「往回跳 40ms」，  
制造出一个可听的重复 —— 实测接缝跳变 **0.08932（曲中 100.0 分位，能听见）** vs 正确写法的  
**0.00162（30.2 分位，听不出来）**，差 55 倍。

**工具链**（`tools/build_bgm.py`，跑法见文件头）：

| 环节     | 怎么做的                                                                                                                 |
| ------ | -------------------------------------------------------------------------------------------------------------------- |
| 裁 + 接缝 | `tools/build_bgm.py`（numpy 算，采样级精确）                                                                                  |
| 编码 Ogg | **借 Blender 内置的 `aud` 模块**（`CODEC_VORBIS` / `CONTAINER_OGG`）—— ⛔ 本机**没有 ffmpeg**，pip 也完全不通（Python 侧装不了 soundfile 之类） |
| 循环开关   | `assets/audio/bgm_main.ogg.import` 里 **`loop=true`** —— ⛔ **默认是 `false`**，不改的话音乐播完就彻底哑，而且**不报任何错**                   |
| 播放     | `scripts/audio_manager.gd`（autoload 名 `Audio`），一进游戏就满音量起播                                                            |

**接线规矩**：每个「页面入口」都显式点一次 `Audio.play_bgm()`（`app.gd` 的 `show_entry()` / `_load_act()`、  
`frontend.gd` 的 `_set_page()`）—— 将来加分支才不会漏掉音乐。同一首重复点会自己 `return`，  
不会把音乐一次次打回开头。

⛔ **两条铁律**（改 `audio_manager.gd` 时别改回去）：

- 切歌必须**交叉淡化**（旧的淡出的同时新的淡入）。**绝不能**写成「旧的先淡完 → 新的再淡入」——  
  中间那一拍两边都没声，音乐就断了。
- 淡化补的是**线性增益**，不是 `volume_db`：补 db 的话两首各自的增益会掉到 ~0.0056，  
  合起来比正常低约 31 dB，耳朵听到一个「空下去」的口子。用 sin/cos 等功率曲线  
  （`sin² + cos² = 1` → 合成增益全程恒定）。  
  现在只有一首曲子、用不上，但接口已按这个写好，加第二首直接可用。

**验证**：`scenes/_bgmcheck.tscn` 把播放头挪到结尾前 1.5 秒、盯 3 秒，确认  
① `loop` 真的开着、② 播放没中断、③ 播放位置**真的绕回了开头**（期望打印 `BGM_CHECK_OK`）。  
`.import` 里的 `loop=true` 只说明**设置**对，不代表**播起来**接得上 —— 这个必须实测。

音量在 `audio_manager.gd` 的 `VOLUME_DB = -8.0`（素材整段 RMS ≈ −16.6 dB，再压低一档当背景，  
不压过将来的音效）。

⚠ 跑完脚本时偶尔会打印 `resources still in use at exit` —— 那是 Godot 关音频子系统跟资源缓存  
抢顺序（脚本里已经调了 `Audio.shutdown()` 尽量规避），**对游戏没有任何影响**，不用管。

待机动作那一段（`[8c]`，2026-10-05 加）钉的是：**四个 NPC 都挂了脚底枢轴**、  
**枢轴真的在动**（量 25 帧里起伏+摇晃的变化量，不能只检查「有没有挂上」）、  
**每个人的相位不同**（否则四个人像三胞胎同步做操）、  
**老板的呼吸幅度比别人小**（他是在休息，不是在站着）、  
**走近会转头看你、走开转回去**、**被点会「一顿」且自己收回去**、  
以及**点 NPC 仍然能弹出面板**（回归：枢轴插进来之后 `_grey()` 一度找不到灰盒、把自检整个搞崩过）。

> **⛔ 「不许飘」那三条是本轮加的核心回归**（`[8c]`）：  
> **站在身边 150 帧内脚底一共只动 ≤ 8 毫米**、**枢轴从不往上抬**（只会往下沉）、  
> **站在 3.6 米外几乎不转头**（< 6°，上一版在这个距离已经猛拧到 116°）、  
> **被点「一顿」也不会把人弹起来**。  
> ⚠ 量脚底用 `_vis_bounds()` —— 取**局部包围盒的底面中心**，**不要取 8 个角**：  
> AABB 是个松垮的盒子，身体一倾斜那些角就甩出十几毫米的假位移，  
> 第一版就是这么把「已经修好了」的新代码误判成 FAIL 的。

思考框那一段（`[8d]`，2026-10-05 加）钉的是：**四个 NPC 头顶都挂了框**、  
**站远了框自己收回去（进度 0）**、**走近了自己弹出来（进度 1）**、  
**弹出距离读的是 `objects.json` 的 `_bubble.range`**（不是写死在代码里）、  
**框里内容现在确实是空的**（等你给文案）、  
以及**弹出来之后是真的可见、尺寸到位**，  
并且**贴图真的是画出来的** —— 把贴图抽样数不透明像素（> 300 个），  
因为贴图是运行时按参数现画的，画空了必须当场报出来。

`[8e]`（同一天加，形状从「四个共用一张」改成一人一个）钉的是：  
**四个人的形状就是参考图第一列那四个**（星芒 / 方框+尾巴 / 云朵+射线 / 斜格面板，  
逐个跟 `objects.json` 对）、**四张贴图互不相同**（抽样数不透明像素，四个数必须都不一样 ——  
否则就是四个人偷偷共用一个形状）、**四个框是一个量级**  
（0.62~0.67 米，最大/最小 < 1.4 —— 防止某个人头上顶个巨大的框）、  
以及**框的下沿都在头顶之上**（最低 0.70 米 > 半身高 0.65，别糊在脸上）。

> **踩过的坑**：断言里**别硬数帧**。一开始写的是「等 80 帧」，headless 下的实际帧率  
> 跟带窗口时不一样，同样的 80 帧有的机器收得回去、有的收不回去 —— 改成  
> `_wait_until(条件, 上限帧数)` 之后才稳定。  
> 另外「远处」要挑一个**真的在 2.4 米环外**的点：出生点离凤凰男只有 1.5 米，  
> 拿它当「远处」是错的，他当然还在看你。

> **踩过的坑**：自检脚本里 `main` 声明成 `Node3D`，`main.room_size` 是动态属性 ——  
> 用 `var x := main.room_size.z` 会报「Cannot infer the type」。必须写成 `var x: float = ...`。  
> 同样的坑还有 `var p := main._npc_nodes["feng"].global_position` —— `Dictionary[key]` 是  
> Variant，推不出类型，得先 `var host: Node3D = main._npc_nodes["feng"]`。  
> 而**一旦自检脚本解析失败，主场景起不来、脚本自己会一直挂着不退出**（不是报错退出，是永远等），  
> 看着像卡死。所以自检卡住不返回时，第一件事就是去看有没有 `SCRIPT ERROR / Parse Error`。

## 打 Windows 包时注意

`data/*.json` 要打进包。项目设置 → 导出 → 资源 → 「导出时包含的文件过滤」加上：

```
data/*.json
```

`*.tscn` / `*.gd` / `*.json` / `*.ogg` 是资源，会被扫进去；但保险起见加一条过滤。  
字体不用打包 —— HUD 用 `SystemFont` 取系统里的「微软雅黑」。  
要发给别人的话，把字体放到 `assets/font.ttf`，HUD 会优先用它。
